Этот файл — короткая точка входа. Подробная история решений и инцидентов
находится в `AI_CONTEXT.md`. Не перечитывать весь репозиторий без необходимости:

## Приоритет 1 — новая нода Vyrex

Цель: не верить рекламной цифре 50 Гбит/с, а проверить ноду как кандидата в
production. Покупать сначала только один сервер/одну ноду, не переносить туда
весь трафик и не удалять текущие ноды.

1. Получить от владельца доступ к новой VPS и её публичный домен.
2. Добавить RemnaNode отдельным профилем и internal squad без изменения UUID
   пользователей и URL подписок.
3. Сначала скрытый canary/тестовая выдача, затем небольшой процент пользователей.
4. Не менее 72 часов собирать: loss, jitter, p50/p95 latency, скорость до РФ,
   CPU steal, нагрузку, YouTube/Instagram, Gemini/Claude, TCP Reality, Hysteria2,
   UDP и вечернюю деградацию.
5. Сравнить с Францией, Финляндией и Германией. Только после отчёта решить:
   production, резерв или отказ.
6. Не размещать все ноды у одного провайдера/ASN.

## Приоритет 2 — аудит проектов BEDOLAGA

Репозитории:

- `https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot`
- `https://github.com/BEDOLAGA-DEV/bedolaga-cabinet/`

Работать как с источником идей, а не заменять ArcVPN целиком.

1. Зафиксировать лицензии, актуальность, активность разработки и стек.
2. Составить таблицу функций: уже есть в ArcVPN / лучше у BEDOLAGA / отсутствует.
3. Отдельно проверить безопасность: auth, права администратора, webhook,
   платежи, хранение токенов, SQL/command injection, SSRF, rate limits.
4. Выбирать модули по полезности: Remnawave integration, lifecycle пользователей,
   nodes/hosts/squads, статистика, рассылки, support, payments, backups, audit.
5. Не копировать код до проверки совместимости лицензии.
6. Переносить по одному модулю через адаптеры и тесты, сохраняя текущую БД,
   подписки, платежи и работающий production.

Результат аудита: отдельный markdown с матрицей функций и решением
`взять / адаптировать / не брать` для каждого существенного компонента.

## Приоритет 3 — безопасная очистка локального проекта

Очистку выполнять только после аудита и отдельным коммитом.

1. Снять `git status`, классифицировать каждый tracked/untracked файл.
2. Ничего не удалять массово и не считать незакоммиченные файлы мусором.
3. Для каждого кандидата определить: source, production asset, generated,
   diagnostic, secret, obsolete или unknown.
4. Сначала улучшить `.gitignore` для логов, `.arcshots`, временных сборок,
   worktrees и локальных диагностических файлов.
5. Нужные изображения перенести в понятную структуру `webapp/public/assets/...`;
   документацию сгруппировать, но не ломать ссылки.
6. Секреты убрать из tracked-файлов и при необходимости ротировать.
7. Перед удалением создать список кандидатов и получить подтверждение владельца
   для всех неоднозначных файлов.
8. После очистки прогнать тесты, сборку WebApp, запуск бота/subscription API и
   проверить production deployment.

На момент handoff рабочее дерево содержит пользовательские untracked assets,
логи и диагностические файлы. Они не принадлежат автоматически агенту и не
должны удаляться без классификации.

## Правила работы нового чата

- Сначала диагностика и воспроизводимый факт, затем изменение.
- После изменения: локальная проверка → commit → push → `git pull` на production
  → restart нужных services → проверка публичного результата.
- Не менять одновременно панель, подписку и БД без rollback-плана.
- Не публиковать пароли, API tokens, subscription IDs и private Reality keys.
- Обновлять `AI_CONTEXT.md` только фактами, которые пригодятся следующему чату.
- Сохранять краткие отчёты: причина, исправление, проверка, commit.
