# План добавления нового сервера ArcVPN

Этот документ — повторяемый чек-лист для новой страны/ноды. На один сервер создаются **4 пользовательских подключения**:

1. XHTTP Reality — основной автоматический выбор.
2. TCP Reality — совместимый запасной вариант.
3. Hysteria2 — скоростной UDP-вариант.
4. Обход глушилок (LTE) — отдельный CDN-вход.

Не хранить в этом файле пароли, UUID, ключи Reality, токены подписок или приватные IP-доступы.

---

## 1. До начала работ

- [ ] Добавить сервер в `servers` БД бота и проверить доступ панели 3x-ui.
- [ ] Создать прямой домен ноды: `<country>.arccnet.space` → IP сервера.
- [ ] Выпустить Let's Encrypt-сертификат для прямого домена.
- [ ] Для LTE создать **отдельный CDN-ресурс** и домен `cdn-<country>.arccnet.space` с origin на эту ноду.
- [ ] Проверить DNS, TCP/UDP 443, HTTP 80 для ACME.
- [ ] Сделать резервные копии `/etc/x-ui/x-ui.db` и `/root/ArcVPN/database/vpn_bot.db`.

Рекомендуемый короткий код страны: `fi`, `de`, `nl`, `pl` и т. п. Прямой домен используется Hysteria, CDN-домен — только LTE.

## 2. Четыре inbound

### 2.1 XHTTP Reality — основной

| Поле | Значение |
|---|---|
| Protocol | `vless` |
| Transport | `xhttp`, mode `auto` |
| Security | `reality` |
| Port | `12631` (если свободен) |
| Remark | `<флаг> <Страна> ⭐⚡ [АВТОВЫБОР]` |
| Назначение | Основной профиль для большинства клиентов |

Reality-ключи и `shortId` должны быть уникальными для inbound. Не добавлять `xtls-rprx-vision` в XHTTP-конфиг.

### 2.2 TCP Reality — запасной

| Поле | Значение |
|---|---|
| Protocol | `vless` |
| Transport | `tcp` |
| Security | `reality` |
| Port | `2087` (или другой свободный отдельный TCP-порт) |
| Remark | `<флаг> <Страна> #1` |
| Назначение | Совместимость и резерв для сетей, где XHTTP нестабилен |

Для TCP Reality — отдельная пара ключей и отдельный `shortId`. Перед массовой выдачей проверить на мобильной сети.

### 2.3 Hysteria2 — скорость

| Поле | Значение |
|---|---|
| Protocol в 3x-ui | `hysteria`, version `2` |
| Пользовательский порт | UDP `443` |
| Прямой host/SNI | `<country>.arccnet.space` |
| Remark | `<флаг> <Страна> #2⚡` |
| Назначение | Видео, большие загрузки, нестабильные сети |

Текущая продовая схема ArcVPN:

- 3x-ui inbound Hysteria хранит клиентов и остаётся на UDP `8443`.
- Реальный пользовательский UDP `443` обслуживает официальный `hysteria` v2 через `arcvpn-hysteria.service`.
- Скрипт `/usr/local/lib/arcvpn-hy2-auth.py` проверяет `settings.clients[].auth` в `/etc/x-ui/x-ui.db`.
- В подписке Hysteria всегда выдаётся прямой домен и порт `443`.
- Не использовать `password` вместо `auth`: в 3x-ui v3 это разные поля. Для v3-подписки нужно брать inbound-специфичный `auth`.

Перед выдачей проверить официальный клиент Hysteria: подключение, SOCKS и HTTP-трафик. Только затем добавлять inbound всем клиентам.

### 2.4 Обход глушилок (LTE) — CDN

| Поле | Значение |
|---|---|
| Protocol | `vless` |
| Transport | `xhttp`, mode `packet-up` |
| Security на origin | `none` |
| Origin port | `10001` |
| Внешний host/SNI | `cdn-<country>.arccnet.space:443` |
| Remark | `🇷🇺 Обход глушилок (LTE) #<N>` |
| Назначение | Белые списки/CDN для проблемных LTE-сетей |

CDN-ресурс обязан проксировать HTTPS на origin этой конкретной ноды. В custom-подписке подменять IP origin на CDN-домен, TLS и SNI. Встроенная подписка 3x-ui для LTE непригодна: она выдаёт прямой IP и `security=none`.

## 3. Порядок и дизайн подписки

Порядок должен быть одинаковым в панели и в кастомной подписке:

1. `<флаг> <Страна> ⭐⚡ [АВТОВЫБОР]` — XHTTP Reality.
2. `<флаг> <Страна> #1` — TCP Reality.
3. `<флаг> <Страна> #2⚡` — Hysteria2.
4. `🇷🇺 Обход глушилок (LTE) #<N>` — CDN/LTE.

Для нескольких стран сначала группировать автоматические XHTTP-профили, затем TCP, Hysteria и LTE согласно заданному порядку панели. Логика сортировки должна игнорировать флаги, но сами флаги оставлять в отображаемом имени.

Инфо-текст подписки:

```text
❗ Не работает VPN? Жми кнопку - 🔁 обновить подписку.

🔥РФ сервисы РАБОТАЮТ с VPN
⚡ — скорость
⭐ — надёжность
LTE — обход глушилок (белые списки)
```

Заголовок: `ArcVPN 🌟`.

## 4. Выдача всем клиентам

После проверки четырёх inbound:

1. Сделать бэкапы БД master и ноды.
2. В 3x-ui v3 привязать активных клиентов к новым inbound штатным endpoint `clients/{email}/attach`.
3. Не использовать старую обёртку `clients/update` для бэкфилла: текущая панель может вернуть `client email is required`.
4. Проверить количество клиентов на master inbound и на физической ноде.
5. Перезапустить `arcvpn-subscription.service`.
6. Открыть тестовую custom-подписку `/sub/<sub_id>?format=plain` и убедиться, что в ней есть 4 новых профиля.

`sub_id`, UUID и срок ключа не менять — пользователям достаточно нажать «Обновить подписку».

---

## 5. Проверка перед анонсом

- [ ] XHTTP Reality: подключение и загрузка сайта с мобильной сети.
- [ ] TCP Reality: подключение и загрузка сайта с мобильной сети.
- [ ] Hysteria2: проверка официальным клиентом и одним мобильным клиентом; UDP/443 слушается официальным сервисом.
- [ ] LTE: тест через CDN-домен, не через IP origin.
- [ ] Проверить, что Hysteria-ссылка использует `auth`, а не `password`.
- [ ] Проверить выдачу custom-подписки: host, SNI, порт и remark каждого профиля.
- [ ] Проверить стандартную страницу 3x-ui: имена и порядок понятны, но LTE на ней не рекомендовать пользователям.
- [ ] Проверить логи `x-ui`, `arcvpn-hysteria.service`, `arcvpn-subscription.service`.

---

## 6. Откат

Если новый inbound ломает выдачу или соединения:

1. Отключить только новый inbound в 3x-ui.
2. Для Hysteria остановить `arcvpn-hysteria.service` только на новой ноде.
3. Восстановить только заранее созданную копию нужной БД.
4. Перезапустить `x-ui` и `arcvpn-subscription.service`.
5. Проверить, что старые профили остались в подписке.

Никогда не выполнять массовое удаление inbound или клиентов без проверенной резервной копии.
