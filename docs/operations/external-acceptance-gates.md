# ArcVPN: внешние критерии production-приёмки

Этот документ перечисляет действия, которые нельзя достоверно закрыть только
из репозитория: нужны доменные записи, реквизиты владельца, реальные почтовые и
платёжные системы либо пользовательское устройство. Секреты нельзя отправлять в
чат, issue или коммит; они устанавливаются непосредственно в production env.

## 1. SMTP и вход по email

### Что подготовить

1. Создать отдельный технический ящик, например `login@домен`, а не использовать
   личную почту владельца.
2. У провайдера включить двухфакторную защиту и создать отдельный app-password.
3. Определить точные значения `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`,
   `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_USE_TLS`. Обычно STARTTLS использует порт
   587; implicit TLS — 465. Нельзя одновременно включать несовместимые режимы.
4. Записать секреты непосредственно в защищённый production env-файл с правами
   только для root/сервиса. После изменения перезапустить только subscription API.

### DNS отправителя

1. SPF: добавить TXT, разрешающий выбранного почтового провайдера. На домене
   должен быть ровно один SPF TXT; несколько правил объединяются в одну запись.
2. DKIM: создать селектор у провайдера и добавить выданный TXT/CNAME. Проверить,
   что подпись `DKIM-Signature` появляется в доставленном письме и проходит `pass`.
3. DMARC: начать с `_dmarc` TXT с политикой `p=none`, адресом агрегированных
   отчётов и выравниванием домена. После недели чистых отчётов перейти к
   `quarantine`, затем при уверенности к `reject`.
4. Проверить PTR/rDNS и HELO, если используется собственный SMTP-сервер.

### Приёмочный сценарий

1. Привязать отдельный тестовый email к тестовому Telegram-аккаунту.
2. Запросить код и убедиться, что UI всегда отвечает нейтрально, не раскрывая,
   существует ли незнакомый адрес.
3. Проверить доставку в Gmail, Yandex и Mail.ru, папку Spam и корректность From.
4. Ввести неправильный код, затем правильный; правильный должен сработать один раз.
5. Повторно использовать код — отказ. Дождаться expiration — отказ.
6. Превысить rate limit по адресу и IP — запрос блокируется без отправки писем.
7. После входа проверить, что открыт тот же Telegram user/subscription, а не новый.
8. В логах не должно быть кода, SMTP-пароля или полного email.

## 2. Юридические данные и согласие

Перед публикацией передать и установить: `LEGAL_OPERATOR_NAME`,
`LEGAL_OPERATOR_INN`, `LEGAL_OPERATOR_REGISTRATION`, `LEGAL_OPERATOR_ADDRESS`,
`LEGAL_CONTACT_EMAIL`. Для ИП/ООО указать официальное наименование и применимые
регистрационные данные; для физлица/самозанятого — форму, которую подтвердил юрист.

Приёмка:

1. Юрист проверяет пользовательское соглашение, обработку персональных данных,
   порядок возврата, автопродление и электронные чеки.
2. Страница не содержит заглушек, чужих реквизитов или несуществующего email.
3. У соглашения есть версия и дата вступления в силу.
4. Onboarding сохраняет Telegram user ID, версию и UTC-время согласия.
5. Новая версия требует повторного согласия только когда это юридически нужно;
   старые записи остаются в аудите.
6. Ссылки доступны до нажатия кнопки согласия и открываются без авторизации.

## 3. Промокод и реальная оплата

1. В админке создать одноразовый тестовый промокод с небольшой скидкой, сроком
   действия и лимитом использований 1.
2. Проверить preview: исходная цена, величина скидки и итог совпадают с каталогом.
3. Создать заказ, но не оплачивать: промокод остаётся доступным.
4. Создать второй конкурентный заказ с тем же кодом: окончательное использование
   должно выиграть только одно успешное fulfillment.
5. Оплатить минимальный безопасный заказ либо использовать официальный sandbox
   провайдера. Проверить provider payment ID, сумму и состояние `paid`.
6. Убедиться, что entitlement выдан ровно один раз, промокод погашен после оплаты,
   а повторный webhook не меняет срок и не расходует код повторно.
7. Проверить отменённый, истёкший и возвращённый платёж. Возврат не должен
   самопроизвольно создавать новый entitlement.
8. Сверить чек/назначение платежа и отсутствие карточных данных в ArcVPN-логах.

## 4. DNS v2 canary

1. Выбрать отдельные Telegram ID владельца/тестировщиков и указать их только в
   `ARCVPN_DNS_CANARY_TELEGRAM_IDS`. Глобальный `ARCVPN_DNS_PROFILE=v2` пока не включать.
2. Обновить подписку на Android и iOS либо macOS/Windows, минимум в двух версиях Happ.
3. На Wi-Fi проверить подключение, 30 минут обычной работы, сон/пробуждение,
   смену сети и десять последовательных reconnect.
4. Повторить на LTE/5G. Проверить обычные сайты, Telegram, платежи и RU/private
   домены. Отдельно наблюдать кратковременные потери соединения 5–60 секунд.
5. Убедиться, что Google/Cloudflare IP отсутствуют в выданном v2 JSON, а DNS и
   routing tags соответствуют поддерживаемой Xray-модели.
6. Собрать клиентские логи без subscription UUID. При ошибке удалить canary ID,
   обновить подписку и подтвердить возврат старого payload.
7. Только после успешного canary включить `ARCVPN_DNS_PROFILE=v2`, перезапустить
   subscription service и повторить безопасную публичную проверку.

## 5. LTE-only quota canary

1. До изменения squads сделать backup SQLite и экспорт состояния Remnawave users,
   internal squads и inbound UUID без токена/приватных ключей.
2. Dry-run должен подтвердить четыре main inbound и ровно два LTE inbound:
   `DE_DHOST_LTE_XHTTP`, `NL_DHOST_LTE_XHTTP`.
3. Выбрать Standard-тестера. Зафиксировать основной UUID и subscription URL;
   после миграции они обязаны остаться прежними.
4. Подтвердить в Remnawave две идентичности: main с `trafficLimitBytes=0` и только
   main squad; LTE с 45 GiB и только LTE squad.
5. Обновить подписку. В plain/base64/Happ проверить: обычные профили используют
   старый UUID, LTE-профили — новый LTE UUID; Economy LTE-профилей не получает.
6. Выполнить реальный запрос через main и LTE. В Remnawave main usage не влияет на
   LTE usage bar; LTE usage через минуту совпадает в Remnawave, HTTP header и WebApp.
7. На canary временно приблизить LTE identity к лимиту безопасным тестовым объёмом
   или отдельным малым canary-лимитом. После исчерпания LTE перестаёт работать,
   main остаётся рабочим.
8. Выполнить calendar reset и проверить, что сброшена LTE identity, локальный
   счётчик равен нулю и main UUID не изменён.
9. После 24 часов без mismatch/ошибок применить миграцию ко всем активным users.

Rollback: вернуть main squad прежние main inbounds, оставить main identity
unlimited, исключить LTE links из ArcVPN subscription и отключить LTE identities.
Нельзя удалять или вращать основной UUID/публичный URL.

## 6. Ручная браузерная приёмка

1. `/admin`: войти паролем, закрыть браузер, открыть снова — сессия сохраняется;
   затем выполнить Logout и убедиться, что cookie отозвана.
2. Пройти Tab/Shift+Tab/Enter/Space по login, promo, оплате и admin-навигации;
   фокус видим, порядок логичен, trap отсутствует.
3. Проверить 390x844, 768x1024, 1366x768 и 1920x1080 без горизонтального overflow.
4. Зафиксировать disabled/loading/error/success промокода и email, а также empty
   состояния кабинета. Console не содержит accessibility/runtime warnings.
5. Сохранить скриншоты и время проверки в `.codex/stages/current.md` без пользовательских
   UUID, email, платёжных идентификаторов и токенов.
