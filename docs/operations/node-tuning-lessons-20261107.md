# Настройка и диагностика нод: опыт ArcVPN, 6–7 ноября 2026

Это практическая памятка по результатам чата, а не универсальный «идеальный»
конфиг. Разделять подтверждённые изменения, неподтверждённые гипотезы и ошибочные
замеры. Перед повторением сверять живые конфиги: версии и топология меняются.
Секреты, UUID, ссылки подписок и подписанные адреса медиа здесь не хранить.

## Исходное состояние и обязательные ограничения

- Актуальный worktree: `.arcshots/hostup-release`; control plane — Польша,
  `217.60.33.38`. Старые документы о Германии, Швеции и московском входе могут
  описывать уже отменённые маршруты.
- Royale: `45.141.202.248`, `nl.arccnet.space`, Reality TCP443; AI TCP8444 с WARP,
  игры Hysteria2 UDP443; источник Yandex CDN. Литва: `88.216.62.135`,
  `lt.arccnet.space`. Проверять сертификаты и SNI именно на `.space`;
  ошибочный `.com` из скриншота не является рабочим SNI.
- Московский VPS — сайты, не постоянный VPN-мост. Разрешённый диагностический
  клиент на loopback не должен превращаться в публичный VPN или менять маршруты.
- Сохранять URL подписок, основные UUID, LTE-идентичности, квоты и действующий
  доступ. Отдельный owner squad должен переживать штатную синхронизацию Remnawave.
- По последнему решению владельца флаги отображения: игры 🇫🇮, нейросети 🇺🇸.
  Это подписи профилей, а не обещание физического расположения или миграция VPS.
- Режим economy. Измерения выполнять удалённо, не через Windows/INCY владельца.
- Владелец попросил убрать FinalMask: не возвращать его как «улучшение» по
  старым заметкам. Скриншоты конкурентов дают предмет проверки, но не являются
  инструкциями для изменения нашего production.

## Что реально исправили и перенесли

1. Общий профиль «🇳🇱 Нидерланды» стоит после YouTube и перед Швецией; старый
   одноимённый алиас удалён. Шведский и остальные прежние шведские алиасы теперь
   используют Royale. Отдельный прежний HostUp нельзя считать доступным резервом.
2. Общий Auto: LT/NL leastPing, CDN — резерв только для имеющих LTE-доступ.
   Обычная Литва в JSON направляет YouTube на NL правилом клиента, чтобы этот
   трафик не попадал на LT. В NL выход к YouTube прямой, без RU. Plain/base64
   одиночных ссылок не могут выразить полноценную многовыходную JSON-маршрутизацию.
3. Yandex CDN переключён владельцем с LT на Royale, после чего проверены реальные
   туннели и NL egress. Сохранены домен,14 актуальных/совместимых путей,
   авторизация LTE и ссылки. LT оставлен как готовый источник отката.
4. Royale добавлен в админку; новые операторские результаты CDN относятся к NL,
   история LT сохраняется. Для операторских проверок использовать Latency Lab
   из админки, а не подменять LTE успешным запросом с обычного VPS.
5. У маски Royale исправили403/HTTP1.1 на200/TLS1.3/h2; позднее проверена
   содержательная статическая страница. Полноценная страница лучше технической
   заглушки для корректного маскировочного сайта, но сама по себе не доказывает
   устойчивость к ТСПУ и не гарантирует скорость медиа.

## Reality, SNI и nginx

- На LT и NL собственные SNI, собственные сертификаты и ключи Reality. Рабочий
  fingerprint Firefox; Chrome на затронутых Happ/mobile путях ранее не прошёл.
  Не копировать fingerprint конкурента без реального клиентского допуска.
- Target обычного Reality — локальный TLS nginx `127.0.0.1:8443`. Проверять
  сертификат, SAN, цепочку, срок, TLS1.3, h2 и HTTP200; иметь reload-hook обновления.
- После успешной аутентификации Reality закрывает соединение с маскировочным
  target. Обычный VPN-пayload не проходит через HTTP proxy_buffers/sendfile
  этого сайта. Крутить nginx ради ускорения обычного Reality без доказательства
  узкого места бессмысленно.403 сам по себе не объяснял минутное ожидание видео.
- `worker_processes auto`, `worker_connections768`, большой systemd NOFILE не
  доказали перегрузку. Увеличивать лимиты по наблюдаемым очередям/ошибкам.
- Домен и голый IP сравнивать с одинаковым SNI/UUID/транспортом. DNS-only причина
  периодических сбоев не установлена; смена адреса не является готовым лечением.

## CDN: проверять полезный трафик, а не зелёный пинг

- Прямые origin LT/NL проходили там, где публичный Yandex edge обрывал HTTPS.
  Успешный HTTP204 при неработающем HTTPS — реальная воспроизводившаяся ловушка.
- Для Best/Auto reserve добавлен HTTPS probe на `sub.arccnet.space:18443`;
  старый HTTP18080 сохранён для кэшированных клиентов. Проверять TLS, HTTPS204,
  полный файл, последние байты, вынужденный fallback и восстановление.
- Добавлен альтернативный вход `188.72.110.52` с прежним CDN Host/SNI и LTE UUID.
  Это IP edge, не origin и не новый выход. DNS-кандидаты сохранены. Отдельно
  проверять авторизацию и отсутствие CDN у пользователей без LTE.
- `188.72.103.4` оказался быстрее по части операторских RTT, но хуже завершал
  файлы в контроле; в общий пул не добавлен. Пример конкурента — гипотеза.
- Рабочий packet-up: GET + header placement + `X-Session-Token`; значения должны
  совпадать на inbound, Host и в клиентском extra. Сохранять пути и padding.
- Меньшие chunks, частые H2 reconnect, принудительный ALPN не дали устойчивого
  улучшения. HTTP/1.1 в одном сравнении был особенно плох; не внедрён.
- Новый Xray26.10.31 не показал повторяемого выигрыша против26.7.28. Контроль
  origin проходил у обоих. Не повышать версию только ради обещания скорости.
- Перед сменой группы: резервная копия, новый origin с той же авторизацией,
  реальные пути/egress, готовый LT rollback; после переключения повторить через
  публичный edge. Мониторинг переносить только после подтверждённого NL выхода.

## Автовыбор и конкуренты

Сравнивали свежие Leeroy, NN-ID и архивный Midas, не только последний источник.
У защищённых подписок важен HWID/номер устройства; ошибка лимита устройств не
означает пустой конфиг. Не записывать чужие ключи и URL в отчёт.

- NN-ID:35s/3/10s, ordinary leastLoad maxRTT8s.
- Leeroy: ordinary30s/3/3s, maxRTT1s; CDN20s/2/4s, maxRTT8s.
- Midas (архив): ordinary2m/3/2s, whitelist30s/3/2s.
- ArcVPN: Auto15s/2/5s, Best30s/3/5s. В контролируемом полном отказе
  переключение15s/2 заняло36.1s против69.2s при30s/2. Частые проверки быстрее
  обнаруживают отказ, но расходуют больше фонового трафика; не менять на2мин
  только потому, что так у конкурента.
- Best maxRTT поднят с800ms до3s: рабочие LTE-кандидаты с большим RTT ранее
  отсеивались. Это допуск кандидата, а не ускорение канала.
- Xray мог считать завершённый HTTP503 успешной пробой. Проверять фактическую
  семантику health check, не считать любой ответ доказательством доступа.

## Telegram: методика, ошибки и итог

Ранние замеры без привязки Windows к физическому интерфейсу могли идти через
активный Wintun и лишний VPN-hop. Их нельзя считать чистым сравнением. Кэш
скачанного в приложении ролика также делает повторное открытие плохим тестом.
Владелец запретил использовать ПК как источник следующих измерений.

Правильный удалённый контроль: одна исходная машина в Москве, проверка `ip route`,
тот же core и полный опубликованный профиль, loopback-only SOCKS, проверенный
egress. Новые TCP/MTProto соединения с уникальными nonce; одинаковые HTTP ranges,
точный206/Content-Range/размер/SHA256, порядок ABBA, учёт всех таймаутов.
Не сравнивать только TG→NL: измерять всю цепочку источник→VPN→TG→источник.

Удалённый опыт07:00–07:02UTC7ноября:120/120 свежих nonce-ответов от5DC,
по30 на A/B/NL/LT.3МиБ публичного видео: A6/6 и B6/6 по1.480s,
обычныйNL6/6 по1.425s; LT5/6 по1.824s и один25s частичный таймаут.
Серверный `routeOnly:true` не дал практического выигрыша; в общий prod не внесён.
CPU cap теста не срабатывал. Локального файлового/Telegram-кэша не было, но кэш
серверов Telegram неподконтролен. HTTP публичного MP4 и nonce-проверка не равны
авторизованной перемотке десятиминутного видео. Московский DC не равен домашнему
ISP или LTE владельца. Не объявлять минутную задержку решённой по этим цифрам.

## Что пробовали и что ещё остаётся гипотезой

- CUBIC/BBR: небольшое преимущество меняло знак при перестановке портов; оставлен
  CUBIC. Сравнение разных портов всегда может измерять разную фильтрацию.
- Sniffing с routeOnly сохраняет исходный IP, но не убирает ожидание sniffing
  (бюджет до200ms). Это не установленная причина минутного stall; у native
  MTProto обычно нет TLS SNI. Отрицательный A/B результат нужно сохранять.
- Клиентский TCP keepalive уже45s/45s по default dialer; inbound listener
  keepalive отдельно мог быть выключен. Не считать blanket sysctl готовым
  исправлением. Проверять idle/reconnect отдельным опытом.
- Прямой XHTTP TLS с HTTP/2/grpc_pass и Hysteria2 — следующие независимые
  кандидаты. Предыдущие короткие замеры обещающие, но устойчивый выигрыш на
  удалённой Moscow/native-media цепочке ещё не доказан. Прямой XHTTP не следует
  смешивать с CDN GET/header packet-up. Hysteria уже используется игровым профилем.
- Telegram IP не пересекались с проверенными RU geoip списками; случайный
  direct bypass через geoip:ru не подтверждён. Проверять порядок клиентских
  правил вместо предположений. RU-сайт может иметь собственный WAF.

## Безопасный следующий цикл

1. Прочитать handoff, stage, node contract, сверить живое состояние и сроки VPS.
2. Сформулировать одну гипотезу, один параметр A/B и ожидаемый пользовательский
   эффект. Зафиксировать маршруты, SNI, авторизацию, лимиты, откат и измерения.
3. Отдельный owner-only процесс/identity, root0600, loopback где возможно;
   ограничения CPU/RAM, RuntimeMaxSec и таймер закрытия точных firewall правил.
   Проверять реальный запуск и expiry, не только наличие unit-файла.
4. Учитывать CPU throttling, сетевые очереди, retrans/reordering и фоновую нагрузку.
   Если появился победитель на разных портах — переставить порты и повторить.
5. Для телефона: очистка кэша перед КАЖДЫМ прогоном, закрытие Telegram,
   одинаковый ролик/точка перемотки, A/B/B/A; Wi-Fi/LTE отдельными сериями.
   Не удалять данные приложения, не просить личный ролик/сессию без необходимости.
6. Принимать конфиг по реальному трафику и пользовательскому эффекту. Сверять
   JSON/plain/base64 owner, другой LTE, без LTE; существующие профили должны
   совпадать вне согласованного изменения. Ping не является приёмкой.
7. Commit/push/FF pull, restart только затронутого сервиса. После испытаний
   убрать свои процессы/пути/правила и credentials, сохранить обезличенные
   результаты и ограничения. Не удалять неизвестные файлы.
