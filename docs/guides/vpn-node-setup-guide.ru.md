# Практический гайд: настройка и диагностика VPN-нод

Для владельцев сервисов на Xray/Remnawave и похожих системах.
Версия памятки: 7 ноября 2026 года. Домен `edge.example.com`, имена файлов
и значения в угловых скобках — примеры, их нужно заменить своими.

Задача — получить стабильную работу приложений на сетях пользователей.
Красивый пинг, открытый порт и высокая скорость самого VPS ещё не доказывают
хорошую работу VPN. Единого конфига, идеального для всех операторов, нет.

## 1. Начните со схемы маршрута

Запишите отдельно вход клиента, транспорт, промежуточные серверы и выход:

```text
Обычный профиль: устройство → зарубежная нода → интернет
CDN-профиль:    устройство → CDN edge → origin → интернет
Особый маршрут: устройство → выбранная для приложения нода → приложение
```

Для каждого профиля заполните таблицу:

| Поле | Что указать |
|---|---|
| Адрес подключения | Домен или IP, TCP/UDP-порт |
| Транспорт | Reality/RAW, XHTTP, Hysteria2 и т. д. |
| TLS | SNI, способ проверки сертификата, fingerprint клиента |
| Реальный выход | VPS, дополнительный прокси, WARP или другой шлюз |
| Авторизация | Какой inbound, группа пользователей, отдельная ли квота |
| Резерв | Условие переключения и конкретный запасной путь |
| Откат | Как вернуть предыдущую рабочую схему |

Название страны в приложении не доказывает страну выхода. Проверяйте внешний
IP через готовый профиль. Если трафик должен обходить первую ноду полностью,
правило выбора второй ноды необходимо на клиенте: серверное правило первой
ноды уже предполагает прохождение трафика через неё.

Не добавляйте промежуточный VPS «на всякий случай». Каждый дополнительный
участок должен иметь измеримую цель: доступность, нужный выход или резерв.

## 2. Подготовьте VPS и сохраните исходное состояние

До настройки зафиксируйте:

- ОС, версию ядра, серверного core, панели и клиентов;
- ресурсы VPS, CPU steal, память, дисковое место, условия трафика и срок оплаты;
- текущие сервисы, занятые TCP/UDP-порты, правила firewall и маршруты;
- владельца каждого конфига: панель, агент, provisioning-скрипт или ручная правка.

Минимальные диагностические команды для Linux:

```bash
uname -r
uptime
free -m
df -h /
ss -lntup
ip -4 route
```

Сохраните конфиги и firewall в закрытое хранилище. UUID, приватные ключи,
токены панели и ссылки подписок не должны попадать в публичный отчёт или Git.
Не запускайте автоматическую очистку незнакомых файлов на действующем сервере.

Если конфигом управляет панель, меняйте источник конфигурации. Ручная правка
в контейнере может исчезнуть после синхронизации. После настройки проверьте
не только первый запуск, но и следующий штатный цикл синхронизации.

## 3. Соберите сначала один обычный профиль Reality

Простой старт — один рабочий VLESS Reality без балансировщика и дополнительных
мостов. Для каждой независимой ноды создавайте собственные ключи Reality и
short ID. Выдавайте клиенту только публичную часть и его данные доступа.

Пример фрагмента inbound для схемы с собственным локальным TLS-сайтом:

```json
{
  "tag": "ordinary-reality",
  "listen": "0.0.0.0",
  "port": 443,
  "protocol": "vless",
  "settings": {
    "decryption": "none",
    "clients": [{"id": "<UUID>", "flow": "xtls-rprx-vision"}]
  },
  "streamSettings": {
    "network": "raw",
    "security": "reality",
    "realitySettings": {
      "target": "127.0.0.1:8443",
      "serverNames": ["edge.example.com"],
      "privateKey": "<PRIVATE_KEY>",
      "shortIds": ["<SHORT_ID_HEX>"]
    }
  }
}
```

Это фрагмент, а не полный готовый серверный конфиг. Нужны outbounds,
маршрутизация и ограничения доступа. В разных версиях core встречаются старые
названия полей, например `tcp` вместо `raw`. Проверяйте документацию установленной
версии и экспорт панели, не соединяйте примеры разных версий механически.

Адрес подключения и SNI — разные поля. Можно подключаться к IP, сохраняя
домен в SNI. Это позволяет отдельно проверить DNS, но не гарантирует обход
ограничений или повышение скорости. Сравнивайте варианты с теми же остальными
параметрами. Fingerprint должен поддерживаться конкретным клиентом: универсального
победителя между Firefox, Chrome и другими значениями нет.

Основа и примеры: [официальный проект REALITY](https://github.com/XTLS/REALITY),
[транспорт Xray](https://xtls.github.io/en/config/transport.html).

## 4. Настройте собственный TLS-сайт для выбранной схемы

Этот раздел относится к Reality с собственным локальным target. Он не означает,
что любой Reality обязательно требует собственного домена и сайта.

1. Настройте DNS выбранного домена.
2. Получите сертификат подходящим ACME-методом и настройте продление.
3. Поднимите HTTPS-сайт на loopback-порту, например `127.0.0.1:8443`.
4. Укажите этот target в Reality, а домен сертификата — в разрешённых serverNames.
5. Проверьте сертификат, TLS и ответ сайта как локально, так и снаружи.

На публичном TCP443 в этой схеме слушает Xray. Второй независимый nginx на том
же IP:TCP443 не запустится без специально спроектированного разделения трафика.

Проверки локального target:

```bash
openssl s_client -connect 127.0.0.1:8443 \
  -servername edge.example.com -alpn h2 </dev/null

curl --resolve edge.example.com:8443:127.0.0.1 \
  -I https://edge.example.com:8443/
```

Проверьте SAN домена, полную цепочку, срок сертификата и отсутствие ошибок
верификации; поддержка TLS1.3/h2 должна соответствовать выбранной схеме.
Для проверки сайта используйте также обычный GET: HEAD и GET могут обрабатываться
по-разному. Разместите содержательную статическую страницу вместо ошибки403
или служебной заглушки. Продление сертификата должно сопровождаться корректным
reload процесса, который его читает.

Рабочий сайт не является доказательством защиты от DPI. Он также не доказывает
скорость авторизованного VPN. В обычной схеме Reality маскировочный HTTP-сайт
не является HTTP-прокси для полезного VPN-трафика: его buffers/sendfile не следует
настраивать как средство ускорения всего туннеля.

Параметры TLS и reload проверяйте по
[документации nginx](https://nginx.org/en/docs/http/ngx_http_ssl_module.html).

## 5. Проверьте профиль до добавления Автовыбора

Приёмка одного профиля:

- core принимает конфиг, сервис работает, нужный порт слушает;
- firewall разрешает только запланированные публичные сервисы;
- пользователь действительно авторизован в нужном inbound;
- подписка содержит правильные адрес, SNI, flow и публичные параметры;
- через полученный профиль проходят HTTPS и загрузка файла;
- внешний IP соответствует запланированному выходу;
- переподключение и работа после паузы не требуют постоянного перезапуска VPN.

Синтаксис Xray можно проверить командой вида:

```bash
xray run -test -config /path/to/config.json
```

При использовании контейнера или панели запускайте проверку тем core и с теми
assets, которые реально используются сервисом. Не ограничивайтесь тестом JSON
другой установленной версии.

Проверьте политику для loopback, private/link-local адресов и служебных endpoint.
Ограничения зависят от продукта: корпоративному VPN могут быть нужны приватные
подсети, публичному сервису нельзя случайно открывать внутренние ресурсы.

## 6. Отдельно исследуйте маршрутизацию и DNS

При медленной работе приложения проверьте:

- не уходит ли оно напрямую из-за порядка domain/IP/geoip-правил;
- не переопределяет ли sniffing исходный IP на домен с повторным DNS-разрешением;
- не выбираются ли разные IPv4/IPv6-адреса или разные CDN/DC;
- соответствует ли итоговая клиентская конфигурация настройкам в панели;
- не остался ли лишний промежуточный сервер из старой миграции.

`routeOnly` позволяет использовать результат sniffing для маршрутизации без
обычной подмены назначения на найденное доменное имя. Это отдельная гипотеза,
а не обязательный ускоритель. В одном контролируемом сравнении изменение не
дало заметного выигрыша загрузки. У native MTProto нет оснований предполагать
такую же SNI-механику, как у обычного HTTPS.

Отключение sniffing целиком может изменить доменные ограничения и специальные
маршруты. Проверяйте их повторно. TCP keepalive на клиенте, серверном listener
и системные sysctl — разные уровни; сначала выясните реальные настройки core.

## 7. Добавляйте CDN как отдельный путь

Запишите независимо:

```text
адрес edge → TLS SNI/Host → CDN resource → origin group
→ адрес и порт origin → Host до origin → локальный transport inbound
```

У разных провайдеров различаются доступные методы, таймауты, HTTP/2, ограничения
запросов и поддержка потокового ответа. Транспорт должен быть совместим со всей
цепочкой. Не переносите GET/header packet-up или другое сочетание параметров
из чужой подписки без проверки версии core и возможностей своего CDN.

Сначала проверьте origin напрямую, затем тот же полезный трафик через edge:

1. TLS и HTTPS-запрос.
2. Малый и большой файл, включая последние байты.
3. Несколько новых соединений и длительную передачу.
4. Поведение после паузы и восстановления соединения.
5. Правильную авторизацию и учёт квоты.

HTTP204 на простом HTTP-сайте может работать, когда HTTPS внутри туннеля уже
не работает. Поэтому одного зелёного probe недостаточно.

При смене origin сначала подготовьте новый сервер с прежними путями и
авторизацией; оставьте старый рабочим для отката. Затем переключите группу и
проверьте публичный edge с нескольких точек, включая нужные мобильные сети.
Изменение группы и реальный переход трафика — разные события.

Фиксированный IP edge иногда помогает диагностировать DNS/маршрут, но он может
измениться или иначе обслуживаться провайдером. Не копируйте чужой IP как
универсальную настройку; сохраняйте корректные SNI/Host и резервный путь.

## 8. Настройте Автовыбор под собственные условия

Сначала получите хотя бы два проверенных самостоятельных маршрута. Несколько
названий, ведущих на один VPS, не дают независимого резерва.

Установите цель: минимальная задержка, устойчивость, распределение нагрузки
или резерв при отказе. Уточните семантику стратегии в конкретном core.

- Интервал проверки определяет компромисс между фоновым трафиком и скоростью
  обнаружения отказа. Интервалы15–30сек и1–2мин решают разные задачи.
- Количество проб, timeout и порог RTT оценивать вместе. Рабочая мобильная
  нода может иметь высокий RTT: слишком строгий порог исключит её из выбора.
- Проверка каждые15сек не означает мгновенного переключения за15сек.
- Выбранный probe должен обнаруживать нужный класс отказа. Проверяйте, что
  core считает успешным ответом: HTTP-ошибка иногда тоже завершает пробу.
- Если резерв платный или ограничен квотой, не выдавайте его пользователю,
  который не имеет соответствующего доступа.

Обязательно воспроизведите основной отказ, отказ одного резерва, отказ всех
путей и восстановление основного. Фиксируйте реальное время и выбранный маршрут.
Уточняйте поведение уже открытых соединений отдельно от новых.

Схемы полей и смысл probe:
[документация Xray Observatory](https://xtls.github.io/en/config/observatory.html).

## 9. Как честно проверять Telegram и видео

Проверяйте всю цепочку:

```text
источник в сети пользователя → VPN → сервер приложения → VPN → источник
```

Скачивание только с Telegram на зарубежный VPS не измеряет доставку пользователю.
Удалённый тестовый клиент в нужном регионе полезен, но сервер в датацентре не
воспроизводит домашнего или мобильного оператора автоматически.

Перед замерами исключите уже работающий VPN на исходной машине. Проверьте
маршруты до всех тестируемых нод. Если путь нельзя однозначно подтвердить,
такой тест не используйте как чистое сравнение.

Для ручного A/B:

1. Один телефон, одна сеть, неизменные настройки приложения.
2. На время сравнения отключите автозагрузку проверяемых медиа.
3. Перед КАЖДЫМ прогоном очистите локальный медиа-кэш и полностью закройте
   приложение. Не удаляйте данные приложения и не выходите из аккаунта.
4. Переключите профиль, откройте тот же ролик и сразу перейдите на фиксированную
   отметку. Измеряйте время до воспроизведения и зависания.
5. Порядок A/B/B/A, затем другой ролик. Wi-Fi и LTE — отдельными сериями.

Для автоматизации используйте новые соединения, проверенный внешний IP,
одинаковые ranges, HTTP206, Content-Range, точное число байтов и контрольную
сумму. Не скрывайте неудачные запросы за медианой успешных.

Новый nonce в MTProto подтверждает свежий обмен, но не измеряет загрузку
авторизованного видео. Публичный MP4 по HTTPS — другой путь, чем получение
медиа приложением. Заголовок no-cache не гарантирует холодный серверный кэш.
Записывайте эти ограничения рядом с результатами.

| Профиль | Сеть/оператор | Успешно/всего | Первый байт | Полный объём | Паузы/ошибки |
|---|---|---:|---:|---:|---|
| A | … | … | … | … | … |
| B | … | … | … | … | … |

## 10. Что имеет смысл исследовать после базовой настройки

| Гипотеза | Что измерять | Типичная ошибка |
|---|---|---|
| Другой VPS/маршрут | Полную цепочку в нужном регионе и время суток | Смотреть только speedtest самого VPS |
| Прямой XHTTP TLS | Короткие запросы, длительную загрузку, клиентскую совместимость | Смешать его с другим CDN packet-up режимом |
| Hysteria2 | UDP-доступность, потери, стабильность и расход трафика | Считать UDP одинаково доступным у всех операторов |
| CUBIC/BBR | Повторные передачи, latency под нагрузкой, повторяемые A/B | Объявить победу по одному короткому скачиванию |
| Keepalive | Простой соединения, восстановление, смену сети | Поменять sysctl, не проверив socket options core |
| Лимиты nginx/сервиса | Очереди, ошибки FD, CPU, память | Увеличивать все лимиты без признаков насыщения |
| Новая версия core | Тот же путь и клиент, регрессии, полный файл | Приравнять новую версию к ускорению |

Hysteria2 — самостоятельный транспорт; его развёртывание и сертификаты
проверяйте по [официальному руководству сервера](https://v2.hysteria.network/docs/getting-started/Server/).
Ни один из пунктов таблицы не является обязательным улучшением для каждой сети.

## 11. Испытывайте изменения отдельно от пользователей

Создайте отдельный тестовый профиль и, если возможно, отдельный процесс с
временной авторизацией. Публичная подписка обычных пользователей должна
сохраниться. Ограничьте доступ, CPU/RAM и время работы теста.

Заранее настройте отключение временного сервиса, закрытие только его firewall
правил и исчезновение профиля из выдачи. Проверьте поведение после перезагрузки.
Просто истёкший профиль в панели не всегда останавливает отдельный процесс.

Меняйте один параметр. Если A/B находятся на разных портах, повторите опыт с
перестановкой портов: оператор может по-разному обрабатывать эти соединения.
Одинаковый VPS не устраняет конкуренцию за физический канал. Проверяйте CPU
throttling, память, packet loss/retransmission/reordering и фоновую нагрузку.

Переход на общую выдачу оправдан после повторяемого результата и проверки
реальных клиентов. Сравните JSON, обычные ссылки и base64; проверьте разные
тарифы, права на резерв и устройства. Не меняйте UUID и ссылки ради косметики.

## 12. Что сохранить для следующего администратора

Один короткий отчёт на изменение:

```text
Проблема и условия пользователя:
Схема до / после:
Версии сервера и клиента:
Единственный изменённый параметр:
Источник и подтверждённый маршрут измерений:
Успехи / ошибки / таймауты / медиана / хвост задержек:
Какие виды кэша контролировались:
Что не проверено:
Файлы, сервисы и настройки, которые изменены:
Способ и срок отката:
Результат после штатной синхронизации:
Решение: оставить / откатить / продолжить исследование:
```

Отрицательные результаты тоже сохраняйте. Это предотвращает повторное
внедрение настроек, которые уже не помогли, и делает следующий эксперимент
короче и точнее.
