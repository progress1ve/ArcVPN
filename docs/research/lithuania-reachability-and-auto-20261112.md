Проверка Литвы на интерфейсе eth0 в 16:27 МСК увидела контрольный SYN из Польши. Во время тех же проверок пакетов с двух опубликованных IP московских проб не было, а обе пробы вернули тайм-аут. Это ограниченный вывод: Check-Host может использовать другие адреса выхода. LT слушает TCP 443, UFW разрешает порт, RemnaNode без рестартов. Сертификат TLS содержит имя LT в SAN. Рабочий путь из Польши подтверждает состояние ноды и авторизацию. Проблема на московских маршрутах начинается раньше сайта или Reality. Источник ограничения на пути остаётся неизвестным.

На 16:16 МСК запись fleet monitor показывала 828 последовательных наблюдений с признаком possible_ip_block и началом текущего эпизода 8 ноября в 22:13 МСК. База хранит последнее состояние, журнал за период не показал переходов LT, отдельной истории по этому адресу в таблице LTE-проверок нет. Сообщённый владельцем промежуток восстановления по этим данным не восстановлен. Оповещение требует трёх подтверждённых отказов, восстановление двух успешных замеров. Неполный ответ внешнего сервиса остаётся неопределённым. [Логика мониторинга](../../monitoring/fleet_alerts.py)

Следующий шаг для восстановления — передать Cherry Servers адрес назначения, время, московские исходные сети и успешный польский контроль, попросить проверить входной маршрут и фильтрацию. После исправления подтвердить TCP 443, HTTPS и реальный туннель с затронутой сети. Если провайдер предлагает другой IP или маршрут, сначала проверить его как ограниченный тестовый вход. Для переноса клиентского трафика нужна согласованная схема с сохранением идентификаторов, подписок, авторизации и откатом. Литву сейчас не перезапускали. Состояние рабочего VPN-маршрута для Москвы не восстановлено.

## Auto и резерв

| Профиль | Интервал / выборка / тайм-аут | Политика |
| --- | --- | --- |
| ArcVPN обычный | 30 с / 3 / 5 с | LT/NL/SE, leastLoad, expected 2, maxRTT 3 с. Запасной выход при отсутствии кандидатов снова NL |
| ArcVPN LTE | 15 с / 2 / 5 с | LT/NL/SE, тот же leastLoad, затем четыре XHTTP-варианта CDN через leastPing |
| ArcVPN «Лучший обход» | 30 с / 3 / 5 с | Четыре XHTTP-варианта, leastLoad, expected 2, maxRTT 3 с |
| NN-ID обычный | 35 с / 3 / 10 с | Основной DE Reality и отдельная ступень резерва с Trojan/TLS и Reality, expected 1, maxRTT 8 с |
| NN-ID обходы | 30 с / 3 / 6–10 с или 35 с / 3 / 10 с | Отдельные профили и резервы в нескольких сетях |

Обычный Auto и LTE Auto сверены на живом рендерере. Правила YouTube в Auto, SE и LT направляют youtube.com и googlevideo.com напрямую в NL. Отдельный профиль YouTube также зависит от NL. При недоступности NL выбор SE для другого трафика YouTube не восстанавливает. Вариант для теста — сохранить NL первым для YouTube и проверить резерв через SE отдельно на реальном видео и по ожидаемому региону показа. CDN может оставаться отдельной ступенью для клиентов с LTE, если его реальный трафик проходит.

Обнаружен отказ уже настроенного резерва. Из Польши TCP 443 к обоим проверенным CDN-входам истёк по тайм-ауту. С московского VPS публичный HTTPS CDN ответил, а авторизованные XHTTP через основной CDN-адрес и запасной IP не завершили HTTPS-запрос. Прямой URL проверки на контроллере вернул 204 из обеих точек. Это разные проверки: доступность сервера пробы не подтверждает доставку через XHTTP. CDN-origin NL сохранил исходное содержимое ответа на корне и его конфигурация идентична перед выкладкой сайта. Сравнительного туннельного замера CDN непосредственно до выкладки не было. Требуется локализовать сбой на рабочем XHTTP-пути, прежде чем полагаться на CDN при отказе NL.

Рекомендация: обычный Auto оставить на 30/3/5, LTE Auto на 15/2/5. В предыдущем контролируемом тесте 15/2 заметил полный отказ за 36,1 с, 30/2 за 69,2 с. У NN-ID окно Burst Observatory длиннее и допуск RTT шире. Для сравнения стоит менять только один параметр в тестовом профиле. Если нужно снизить частоту проб LTE, сравнить 15/2 и 20/2 на здоровом пути, при принудительном отказе и после восстановления. Измерять время до первой успешной передачи через резерв и фактический трафик. ## ТСПУ и сайт NL

Опубликованные измерения ТСПУ описывают фильтрацию по IP, TLS SNI и QUIC. При обрыве после ClientHello тело HTML ещё не передавалось. Для ноябрьского сбоя ArcVPN нет доказательств влияния языка сайта. Доступ с Билайна в Казани восстановился без изменения сервера. Рабочий резерв в другой сети снижает зависимость от единственного маршрута. [Исследование IMC](https://ensa.fi/papers/tspu-imc22.pdf) · [Измерения OONI](https://labs.ooni.io/ru/post/2024-russia-report/)

Сайт NL выложен из коммита 87ab0079. На публичном имени HTTP возвращает 308 с сохранением пути и параметров. Исключение ACME проверено тестовым файлом и успешным пробным продлением Certbot. На HTTPS включены CSP, защита от встраивания, HSTS на сутки, nosniff и no-referrer. Мобильная форма находится выше. Кнопка примера создаёт изображение и конвертирует его локально. Chrome проверен на 360, 768, 1280 и 1600 px, исходный файл и пример конвертируются, внешних запросов и ошибок нет. Nginx перезагружен только на NL. Резервные файлы сайта и vhost находятся на NL в /root/arcvpn-site-backups/20261112-nl-oh_0het0. Git на контроллере подтянут fast-forward, одновременно в checkout вошёл ранее опубликованный отдельный коммит удаления истёкших тестовых профилей. Сервисы бота и подписок для этого сайта не перезапускались.
