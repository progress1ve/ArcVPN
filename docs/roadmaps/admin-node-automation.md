# Автоматизация нод и тестов в админке — предложение

Статус: план для согласования, не реализован. Не разрешает менять топологию.
Цель: владелец вводит IP и пароль, видит процесс и результат без Codex/терминала.
Никакие новые Codex skills этим планом не создаются.

## Что уже есть

`webapp/src/views/admin/AdminNodes.svelte`: форма IP/SSH user/password и direct,
bridge, warp; выполняет только проверку подключения.
`subscription_api.py`: POST /api/admin/nodes/preflight, диагностика портов,
GET /api/admin/nodes/metrics, RBAC nodes.provision/nodes.diagnose, аудит.
Есть отдельные сценарии установки стран, но нет единой устойчивой очереди
инфраструктурных операций. В preflight отключена проверка SSH host key:
это нужно исправить до сохранения доступа и выполнения root-операций.

## Два исполнителя, не два свободно действующих ИИ

| Исполнитель | Разрешённая работа | Что запрещено автоматически |
|---|---|---|
| Установка нод | Проверка доступа, bootstrap, RemnaNode, Reality, мосты, canary, подготовка подписки | Удаление действующих нод, смена UUID/URL, публикация непроверенной ноды |
| Тестирование | Проверенные модули Multitest, диагностика маршрутов, полные логи и сравнение запусков | Произвольный shell, BBR/IPv6 tuning, изменение firewall/маршрутов, публикация внешних отчётов |

Основа: детерминированные versioned recipes в отдельном worker service на
контрольном сервере Польши. Не запускать длительные тесты внутри HTTP-запроса
или процесса бота. ИИ при желании позже объясняет обезличенные результаты,
но не получает пароль, приватные ключи и полномочия shell.

## Пользовательский сценарий установки

1. IP, порт SSH (22 по умолчанию), логин root, пароль, страна/имя/домен.
   Дополнительные поля раскрываются только при необходимости. Шаблон страны
   может подставлять домен; не угадывать его при конфликте.
2. Проверка SSH fingerprint (первичное доверие через подтверждение владельца
   либо проверенный fingerprint провайдера), ОС/архитектуры, диска, памяти,
   занятых портов и существующих сервисов. Не переустанавливать занятый VPS.
3. Предпросмотр состава: обычная нода, Москва→нода, нода→Москва для YouTube,
   YouTube-балансир, автовыбор, отдельный CDN-обход. Показывать роль/приоритет,
   путь CDN, Host/SNI, коэффициент 1, порядок ручного профиля и rollback.
   Точный default состав и порядок требуют согласования до реализации.
4. «Установить и проверить»: идемпотентный bootstrap, уникальные Reality
   ключи на целевой ноде, Remnawave profile/squad/hosts, мониторинг, мосты.
   До приёмки новый сервер не получают действующие пользователи.
5. Проверки: статус RemnaNode и авторизация, конфигурации/порты, реальный
   туннель и IP выхода для каждого включённого пути, фактическая подписка,
   Москва↔нода, YouTube/автовыбор failover и CDN отдельно. DNS/cert могут иметь
   состояние «ожидает DNS»: остальные независимые шаги продолжаются.
6. «Опубликовать»: одна явная операция после зелёных обязательных gates;
   обновляются нужные пулы/хосты без смены пользовательских UUID, URL и лимитов.
   Блокированный CDN не блокирует обычную ноду, если владелец явно согласовал
   частичную публикацию. Автовыбор приоритет не повышается по одному Speedtest.
7. При ошибке — показать проблемный шаг, «Повторить», «Откатить изменения».
   Откат только ресурсов этой операции; сначала исключить её из выдачи.

Baseline брать из проверенного runtime, а не исторического гайда: сейчас
CDN GET/header/X-Session-Token, отдельный путь каждой ноды. В документации
node-config-contract/cdn-lte ещё остались OPTIONS-примеры; сверить и исправить
при реализации, не переносить их слепо в шаблон нового worker.

## Пользовательский сценарий тестов

- Выбрать одну/несколько нод и модули: RU iPerf (Multitest 5), TLAB (6),
  bench.sh (9); дополнительно IP/доступность сервисов и короткий CPU-тест.
  Для нового тестового модуля сначала ревью, затем добавление в allowlist.
- Сохранять проверенные версии и SHA256 Multitest и вложенных скриптов;
  не выполнять curl|bash/latest из сети при каждом запуске.
- Одна тяжёлая задача на ноду, небольшая глобальная очередь; учитывать
  действующий трафик, cooldown и ограничения провайдера. Показывать оценку
  затрат трафика/диска и общий timeout, не обещать точный объём заранее.
- Вывод терминала в реальном времени, текущий город/шаг, время последнего
  вывода, ожидание/тайм-аут; кнопка остановки убивает только процессы job.
- По окончании: полный читаемый TXT и исходный LOG, копирование, скачивание,
  история и сравнение. Ошибки/пропущенные города не превращать в нули.
- В RU-модуле отдельно объяснять: labels Upload/Download — sender/receiver
  одного направления. Не смешивать с двумя направлениями TLAB/YABS.
- Хранить фактический endpoint/город (включая fallback), время, streams,
  продолжительность и инструмент. Казань/Новосибирск — дополнительные
  именованные тесты, если их нет в выбранном модуле; не подменять город.
- Прямой тест VPS и тест через реальный VPN/мост/CDN — разные категории.
  Проверку Telegram на телефоне не объявлять пройденной серверным iPerf.

## Надёжность и безопасность

Предлагаемые таблицы: infrastructure_nodes, infrastructure_credentials_refs,
infrastructure_jobs, infrastructure_job_steps, benchmark_runs/results.
У job есть queued/running/waiting_dns/awaiting_publication/succeeded/failed/
cancelled/interrupted, heartbeat, lease, idempotency key, actor и resource lock.
После рестарта не повторять незавершённую mutation вслепую: сверка состояния,
затем resume. Lock на целевую ноду и общие ресурсы Москвы/Remnawave/CDN.

Пароль передаётся по HTTPS, не возвращается API и не попадает в localStorage,
логи, очередь аргументов, Git или LLM. На Linux — отдельное шифрованное
хранилище с ключом вне БД/репозитория; Windows DPAPI-файлы нельзя просто
перенести на сервер. По возможности после bootstrap используется отдельный
SSH ключ worker с минимальными полномочиями. Root password не отключать
до проверки нового доступа; срок хранения/удаление явно задать владельцу.
Секреты Remnawave/CDN выдаются только нужному шагу; downloadable logs редактируются
до хранения/отдачи, но не теряют ошибки и результаты измерений.

Owner-only управление, отдельные read/diagnose/provision/publish/cancel права,
CSRF/origin защита, повторная авторизация для публикации/доступа к секретам,
аудит без secrets. Запрет произвольных команд и пользовательских script URLs.
Защита SSRF/DNS rebinding: проверять и закреплять IP, запрещать loopback,
private/link-local/metadata targets; инфраструктурные исключения только по
реестру владельца. Публичный IP не доказывает право администрирования:
требуются доступ и подтверждение владельца, никаких массовых сканирований.

## Этапы реализации и приёмка

1. Согласовать сценарий/состав по умолчанию, хранение доступа и публикацию.
2. Backend foundation: secret vault, строгий SSH trust, устойчивая очередь,
   job API, lock/cancel/audit и heartbeat. Тесты RBAC/CSRF, инъекций, SSRF,
   смены host key, утечек, дублей и восстановления после рестарта.
3. Benchmarks MVP: 5/6/9, история, полный терминал/файлы, ошибки и cooldown;
   проверить на FI/EE, сверить цифры с исходными логами и отмену без ущерба VPN.
4. Provisioner MVP: обычная нода→скрытый canary→явная публикация. Проверить
   на отдельном тестовом VPS, не на действующей ноде, включая повтор и rollback.
5. Полный preset: Москва, YouTube, автовыбор, CDN и DNS/cert. Для каждого
   пути собственный real-tunnel gate; проверить существующих пользователей.
6. Svelte UI и браузерная приёмка 390/768/1280/1600: форма, очередь, ошибки,
   ожидание DNS, остановка/повтор, копирование/скачивание и публикация.
   Это функциональный план; визуальная композиция ещё не утверждена и не
   проверялась в браузере. Стек Svelte сохраняется.

Deploy каждого runtime этапа: tests/build→staged diff→commit/push→Poland
ff-only pull→restart только затронутых services→public/real-user verification.
Откат API/UI не удаляет job ledger и credentials; активные операции сначала
останавливаются безопасно. План внедрения и новые skills требуют согласования.
